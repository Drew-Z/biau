# 项目现状盘点与主站同步规划

## 目标

以各项目当前可核实的进展为依据，更新泊岸主站的项目展示。2026-09-16 已完成盘点和分批规划，用户确认“先更新现有项目的真实进展”。B1 已完成本地验证；B2（泊语、律航、商舱和寻球）及用户确认继续的 B3（游湾、六游戏与主站）于 2026-10-05 本地验收完成。每批独立验收，新增项目和扩大公开体验排在现有事实同步之后。

## 已确认背景

- 主站以产品官网和解决方案展示为定位；项目叙事、身份、发布状态及首页入口分别由既有数据模块维护。
- 产品注册表包含 13 个身份；底层 `projects` 数据包含 16 项，公开目录的 `catalogProjects` 展示 10 个主项目、分为 3 组；另外 6 个游戏保留独立详情，不进入目录卡片。公开项目发布表为 10 个主项目维护入口政策，首页有 9 个项目入口。现有数据已包括工作区内尚未提交的 Roleplay 接入。依据：`src/data/productRegistry.ts:1`、`src/data/portfolio.ts:130`、`:2337`、`src/pages/ProjectsPage.tsx:43`、`src/data/projectPublication.ts:15`、`src/data/hero.ts:37` 及本轮数据检查。
- 现有公开项目审计更新于 2026-08-18，需要与当前源项目和本地主站逐项核对，不能将旧观测视为当前在线保证。依据：`docs/project-publication-audit.md:3`。
- 工作区存在本轮开始前的未提交变更，包括主题排版、项目接入和状态/知识投影；本轮保护这些变更，不代为归属或发布。
- 用户进一步明确：不能仅依靠文档判定项目状态。初盘中的文档结论均为待复核线索；实现、运行、发布和验收证据分别记录。
- B1 实施前已直接读取 GitHub Release API，确认锚学 `v1.0.0` 有公开 APK，字节数和 SHA-256 与当前本地文件一致；同时运行当前代码中的 readiness CLI，实际返回 HOLD 和 6 个阻塞码，不能继续沿用“未发布 APK”或文档中仅有 2 个阻塞码的说法。出处及范围见 [B1 核验记录](b1-verification.md)。

## 需求

- R1：建立项目清单，关联站内身份、源项目位置、主站当前表述和可核实证据；找不到源项目的条目明确标为待核实。
- R2：逐项区分项目完成度、入口可用性和访问条件，记录最新证据的时间与范围。
- R3：按用户选择优先修正现有项目的事实与证据，再为每个项目给出保留、补充、修正、候选接入或暂缓建议，并说明对应主站触点；不以项目数量或全部开放体验作为第一轮成功标准。
- R4：形成可分批执行的计划，明确依赖、优先级、验收标准和发布前需补的证据。
- R5：复用现有项目注册、发布政策和生成流程，覆盖首页、项目列表/详情、状态、站内助手和 sitemap 的一致性。
- R6：改变项目状态前核对当前代码、实际运行检查或产物以及真实发布记录；文档用于导航和历史背景，不独立作为状态结论。未重跑的历史测试必须保留版本、日期和范围。
- R7：B1 处理 F01—F06：修正 Roleplay 技术栈和 health 语义、补正文截图/架构图及 sitemap；更新帆灵 release APK/AAB 事实和分发边界；将锚学公开产物、当前验收结果与静态 Web Demo 分别说明。
- R8：B2 核对四个源项目的实际实现，补工作 Agent/成员权限、法律导入与引用流程、ERP 模式/写入权限、寻球三层实现边界；处理 F07 的无日期故障表述，保留入口政策和历史证据的适用范围。
- R9：B3 逐项核对游湾与六游戏的实际入口、玩法/操作、源码标签、历史发布、本地 Web 包和素材；更新主站三组目录、内容发现、阅读返回、主题与界面语言，区分知航历史验收和潮讯待真实 Edition/Feed。

## 约束与非目标

- 用户已授权按规划更新内容；B2/B3 沿用 B1 的本地交付边界，不自动提交、推送或部署站点，不改写公开状态快照，不新增主站 APK 下载按钮。
- 源项目只读检查，可运行确认无外部写入/模型/设备行为的本地评估器；不修改其他项目，不清理已有目录、worktree 或归属不明文件。
- 不把 HTTP 响应、测试文件存在、产物存在或旧验收记录扩写为当前完整业务可用；不执行生产登录、业务写入、模型调用或发布来补证据。
- 不引入无依据的 CMS、全新项目数据层或 UI 重构。
- 遵守既有展示排除项：`douyu`、`yihuan-helper`、`ques` 不进入公开项目目录。
