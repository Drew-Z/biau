## 2. 什么可以成为主站的新事实

用户要求不能仅依靠文档判定状态。项目同步按不同问题分别取证：

1. 当前代码确认功能和实际接线，产物确认构建存在；二者不能单独证明完整功能可用。
2. 执行可安全复跑的检查，记录输入和范围；历史运行记录只有在版本、产物和时间仍匹配时才能复用。
3. README、任务状态、AGENTS 中的项目状态文字和发布计划都只帮助定位；遇到冲突必须回到代码、评估器、产物和真实发布状态。
4. 实際公开页面与发布 API 确认现在提供什么。已发布不等于验收齐全，验收 HOLD 也不等于产物不存在或网站下线。

每次项目更新准备一个简短资料包：稳定项目 id、源版本/工作树标记、已完成能力、验证日期与范围、公开截图、入口条件、已知限制、下一步。资料包先保存在任务盘点中，不新增运行时数据库或 CMS。

“本轮阅读了源码”的日期不能覆盖 `projectPublication.verifiedAt`。后者对应公开可用证据；源码核对时间写在详情质量说明和审计记录中。历史测试数量必须带日期与版本，不换成没有证据的新数字。

## 3. 既有模块继续各负其责

| 内容 | 权威位置 | 更新方式 |
| --- | --- | --- |
| 产品名称、描述、身份和公开/规划定位 | `src/data/productRegistry.ts` | 保持稳定 id；确有定位变化时在这里统一修改 |
| 项目摘要、技术栈、成果、截图、能力、限制、路线 | `src/data/portfolio.ts` | 在现有 overview/workflow/architecture/quality/limitations/roadmap 内更新 |
| 外部 URL | `src/data/siteLinks.ts` | 只登记已确认的公开入口、文档和证据地址 |
| 成熟度、可用性、访问要求与 CTA | `src/data/projectPublication.ts` | 分别维护，不因源码进展自动解锁体验或下载 |
| 首页项目介绍与选取 | `src/data/hero.ts` | 跟随已核实的摘要更新，首批保持现有顺序和数量 |
| 卡片、详情、状态的公共界面文案 | `src/data/projectInterfaceCopy.ts` 等既有文案模块 | 有标签变化才同步，不在组件重定义产品身份 |
| 可靠性检查、目标和门禁 | `src/data/statusTargets.ts`、`docs/manual-gates.md` | 记录有范围的证据，保留独立产品验收要求 |
| 项目公开审计 | `docs/project-publication-audit.md` | 新旧观测按日期区分；更新结论，不抹除历史记录 |
| 助手知识 | `server/data/public-knowledge*.json` | 从审核后的 source data 运行 `assistant:index` 生成 |
| sitemap | `public/sitemap.xml` | 从项目、状态和已发布文章生成，检查集合覆盖 |
| 公开状态快照 | `public/status/*` | 普通检查只读；只有进入已授权的状态发布步骤才重生成 |

不手工修改生成知识或 sitemap 来掩盖源数据遗漏。内容更新的顺序为：资料包审核 → 权威数据/素材 → 生成投影 → 一致性与页面验证 → 审阅发布差异 → 已授权发布 → 线上复核。

## 4. 首批三个项目的具体改法

### 4.1 Roleplay：完成已有接入的同步

- 沿用 `roleplay-demo` id、现有角色剧场品牌和公开入口。
- 技术栈按当前源码表达为静态 HTML/CSS/JavaScript + Node.js；GLM、会话与部署边界分别描述，不使用 `React-like`。
- 将 `roleplay-library` 现有 PNG/WebP 用于正文真实截图块，并按源码边界补一张原生 SVG 架构图；保留既有流程/数据流说明，不用图片副本伪造第二份证据。
- health 描述限于游客服务回应、当前模型配置与角色数量；不据此表达上游模型长期健康或回答质量。
- 项目与状态 sitemap 补齐。已有 `reliabilityProjects` 包含 Roleplay，可评估将 publication 的状态跳转从总览对齐到已有 `/status/roleplay-demo`，无需新增路由体系。
- 发布状态的任何改变以重新核定的完整证据为准；本次计划不因一个 health 响应提高或降低状态。

### 4.2 帆灵：区分产物进展与分发许可

- 替换“仅确认 debug”的过时表述，说明已有本地 release APK/AAB 和受控构建流程。
- 当前产物存在不等于本轮已验证签名、当前线上后端或完整生成结果。主站公开内容只写到实际已证实的层次。
- 保留“展示页可访问、APK 不公开分发”的两层边界。当前源码里的演示凭据模式与生成流程限制仍需源项目先解决。
- 同步详情、助手摘要、主站的 `/pet-app-showcase/` 以及与这些事实直接关联的门禁说明；历史博客若记录当时情况，保留日期，仅补必要的更新说明。
- 第一批只改 blog-semi 内的副本；源 `gamer` 展示目录的后续同步在该源项目独立处理。

### 4.3 锚学：展示新成果，准确表达当前候选

- 保持“本地优先、来源可核验的学习助手”定位；补齐近期恢复、取消、核验和 UI 完成度的有据进展。
- Web 静态 Demo 与 Android Private Alpha 分开：前者不因 Android HOLD 被改成不可用，后者不因网页可用就获得下载入口。
- 实际 GitHub Release 已发布 `v1.0.0` APK，大小与摘要匹配本地产物；当前 readiness CLI 实跑返回 HOLD，包含产物不匹配和证据过期共 6 个阻塞码。主站说明“已有公开产物、当前验收证据待补齐”，保持官网/Demo/仓库链接，不新增直接下载按钮。
- 源 `CURRENT_STATE.md` 概览 GO、发布计划的旧 HOLD 原因和源 AGENTS 的旧限制均有时效差异。它们只作为冲突记录，实际结论来自本轮执行结果，源文件由源项目自行处理。
- 展示本地工程回归记录时附上来源版本/日期，并说明未在主站同步任务重跑模型、真机或发布验收。

## 5. 第二、三批的内容组织

每个详情优先回答六个访客问题：解决什么问题、目前能做什么、怎样实现、有哪些证据、现阶段限制是什么、下一步做什么。复用现有详情分组，无需再造一套内容模型。

- 泊语补工作 Agent 与能力分配场景；成员、访客和管理员不是同一个访问范围。
- 律航、商舱、寻球保留成熟的工程案例。入口待复核只影响体验承诺，文档和代码事实可以先整理。
- 商舱旧停机结论加观测日期；本轮没有线上检查就不继续使用无日期的“当前停机”。
- 游湾展示集合，各游戏详情展示自己的阶段、试玩版本、操作、设备限制和素材日期。6 个游戏不默认进入 `catalogProjects`，不新增逐游戏 publication 体系；若后续证据表明需要逐游戏独立入口治理，再另行规划。
- 主站案例更新到实际核定的本地/发布版本；知航的产品历史验收与潮讯仍未完成的公开版次分别说明。
- 第一轮不调整首页项目排序。完成事实同步后，再按代表性、材料完整度和公开体验质量评估推荐项目。

B3 核对补充：Next Spacewar 源码标识为 0.17；Spacewar II 的实际入口走 Nokia 系列场景，空格射击而非自动射击。Raiden 评分文案和 intespace 样本门禁不充当发布结论。保留已有五游戏录制，明确 Spacewar II 短视频待补；素材内容日期不冒充采集日，历史 Windows tag 不当作当前 Web 版本。主站三组目录、搜索/阅读返回、三主题和界面语言只描述实际本地实现，不从本地分支推断线上同步。

## 6. 后续文航接入的范围

文航可作为下一轮独立项目接入候选。它已具备文档处理与 Agent 工程底座，近期又形成多企业首次使用和售前响应的本地技术闭环；主站仅写“规划中”不足以表达这些成果。

推荐下一轮资料包包含：一个明确业务场景、上传到引用/人工复核/导出的流程、脱敏截图、架构图、当前受控运行证据、真实服务与客户验收仍未完成的说明。沿用现有 `enterprise-document-agent` 身份；候选案例名称可围绕“企业文档与售前响应工作台”，再进行内容审阅。

是否提供公开只读快照或受控演示，需要在文航源项目明确发布边界后决定。本轮不复用 staging URL 作为公共产品入口，不把合成团队或公开资料演练包当成真实客户成果。画帆也不因注册表已有身份就自动补造产品入口。

## 7. 与现有任务的关系

本任务负责盘点和同步计划，与网站完善路线图 Stage 3 内容展示相关，但不接管其尚未完成的主题任务，也不修改旧任务状态。

- Roleplay 已有 `09-15-roleplay-project-integration` 记录，实施前先核对它与现有未提交接入的交付范围，避免重复建设。
- 源项目存在未提交成果，主站只读取并记录来源，不回写、合并或替源项目宣布发布。
- 真正实施时每次只推进一个可验收批次。需要独立子任务时在开始该批次前创建，并明确文件段落与依赖。
- 初盘时“本地领先 117 个提交”为 9 月 16 日历史观察；B1 收口时 `main` 与已存储的 `origin/main` 相同，线上静态产物对应提交仍未核实。发布前重新核对记录和批准范围，不从本地分支或一次 `git push` 推断已完成上线验收。

## 8. 回退与持续维护

单批回退以该批明确修改的内容和生成投影为单位，保护其他任务已有改动；不使用整文件覆盖来回退共享 `portfolio.ts` 或状态文件。

后续每个源项目完成里程碑、变更入口或更换发布产物时，都用相同资料包更新主站。人工维护一份证据清单已经能够满足第一轮需求；本任务不增加自动发布、定时任务或新的内容后台。
