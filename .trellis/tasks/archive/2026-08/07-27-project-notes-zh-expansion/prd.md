# 项目技术档案中文深化

## Goal

将 `docs/project-notes/` 下的八份项目工程档案统一改写为简体中文，并把基于证据的面试题库从 120 组扩展为 300 组可深入追问的技术问答。

## Requirements

- 八份 Markdown 的标题、章节、说明、表头和问答字段使用简体中文；代码符号、路径、URL、提交 SHA、Evidence ID 和稳定枚举保留原文。
- 保持 Chatus、Anchor、公开助手、AI 日报和跨项目比较的事实边界，不把设计、测试库存或历史观测升级成当前生产事实。
- 面试题库精确包含 300 组：Chatus 65、Anchor 60、公开助手 60、AI 日报 65、跨项目 50。
- 每组问答必须包含范围、问题、深入追问、参考回答、失败场景、验证方式和证据；追问、失败和验证内容必须针对具体主题，不能使用统一占位模板。
- 使用可重复生成的结构化题库来源，校验编号连续、数量精确、字段完整、证据存在且范围匹配。
- 不公开 Chatus 私有仓库、访问材料、成员信息、供应商身份或运维细节；不公开模型端点、密钥、原始错误、提示词或内部运行标识。
- 不调用外部模型、搜索服务或生产 API；本轮写作模式固定为 `Codex-only scaffold/review`，`model channel: none`。

## Acceptance Criteria

- [x] 八份项目技术档案的叙述性内容均为简体中文，技术标识与证据引用保持稳定。
- [x] 四份项目档案均覆盖产品边界、架构、数据流、核心实现、故障恢复、安全、权衡、验证、交付状态、代码入口和面试重点。
- [x] 跨项目文档能够比较状态所有权、证据粒度、失败闭合、执行模型、恢复、隐私投影和技术取舍。
- [x] 题库精确达到 300 组，并按 65/60/60/65/50 分布；编号从 `001` 连续到各范围目标编号。
- [x] 每组题目均包含七个中文字段，回答、失败场景和验证方式满足最低信息密度且引用已登记证据。
- [x] `docs:project-notes-check` 能阻止数量回退、断号、英文旧字段、缺失细化字段、未知证据和不安全内容。
- [x] `npm.cmd run docs:project-notes-check`、`npm.cmd run lint`、`npm.cmd run build` 和 `git diff --check` 通过。

## 边界说明

- 题库用于仓库内技术复盘与面试准备，不作为生产能力声明。
- AI 日报必须保持当前事实：生产摄取已取得有效证据，真实生成仍在 Responses 请求边界失败，生成开关已关闭，没有生成或发布日报。
