# 公开助手数据库防护补齐

## 目标

后续上线的请求、回答版本、分支表及两个触发器函数应持续符合服务端专用数据库的权限边界，且保留公开助手的正常持久化行为。

## 范围与约束

- 处理三张表缺少 RLS、两个函数未固定 search_path，以及现有运维检查未覆盖共库 RAG 表的问题。
- 续作实查发现独立 Studio 库 40 张表未开启 RLS，且 anon/authenticated 有 schema 和表权限。将同一服务端专用边界覆盖该库，保留全部历史数据和表。
- 不修改历史迁移，不创建宽松 policy，不使用 FORCE RLS 或 SECURITY DEFINER。
- 真实模型调用和 embedding 调用预算均为 0；不调整渠道或业务开关。
- 生产变更前保留可恢复备份与旧部署版本；现有青珑和 UI 改动由其他会话负责。
- 日报仅复用已有任务观察真实 schedule，不以手动运行替代定时验收。

## 验收

- [x] 新数据库和升级数据库均自动开启三表 RLS，函数解析路径固定且不受调用者或临时表影响。
- [x] anon/authenticated 无三表读写及两个函数执行权限，数据库 owner 正常工作。
- [x] 空库、旧数据升级、不可变回答、跨会话拒绝、整会话删除均通过真实 PostgreSQL 测试。
- [x] 运维脚本明确接受 28 张基础表或加上完整 6 张 RAG 表；未知、缺失、错误 owner 和禁用触发器仍失败。
- [x] 本地备份成功恢复验证，生产迁移后权限、触发器、安全 advisor 和服务健康复核通过（Render 门禁/远端 health；本机直连限制见 verification.md）。
- [x] 持续集成执行数据库回归，相关检查和构建通过；变更精确提交并推送。
- [x] Studio 40 张表与四个触发器函数完成防护，未来对象默认权限也不开放 Data API；备份恢复、正常 owner 读写和 Render `/health` 部署门禁通过。
