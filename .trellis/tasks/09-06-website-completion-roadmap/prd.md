# 网站完善路线图

## Goal

将 BIAU Port / 泊岸从“功能齐全的项目展示站”逐步完善为稳定、易浏览、内容可信、可持续维护的公开产品与工程展示网站。主任务持续评估项目现状，每次选择一个有证据、可独立验收的子任务，完成后回到主任务重新评估并继续执行。

用户已确认主要成功标准为“项目理解与内容发现优先”。合作咨询转化和 AI 产品扩张不作为本阶段的主线。

## Confirmed Facts

- 项目是 React、Vite、TypeScript、自定义 CSS 设计令牌和 `lucide-react` 构成的单仓库网站。
- 当前公开入口包括首页、项目集、项目详情、知识库/博客、AI 日报、可靠性状态页和公开研究助手；Studio 与 Logo Lab 属于内部或评审入口。
- 项目已经具备三主题、响应式导航、博客搜索/筛选/分页、公开助手、状态合同、SEO/分析检查和一套 Playwright UI 检查。
- 当前工作树保留一批尚未交付的 UI 修改，以及持续 UI 回归任务 `09-04-continuous-ui-quality-loop`；本总任务不得覆盖、回滚或混入这些改动。
- 现有记录显示 AI Daily 仍处于“生产待验收/公开 Feed 关闭”状态；公开助手已有产品可用记录，但线上状态需要在专门任务中重新复核。
- 项目已有明确的公开安全边界：不公开密钥、私有数据、未批准内容、未验证下载和内部后台入口；生产平台操作、真实模型调用和公开发布需要单独批准。
- 2026-09-08 用户明确要求建立并执行上述循环，普通范围内的子任务不再逐轮等待“继续”；这同时授权规划、启动、实现、验证和按白名单进行本地提交。
- 当前本地基线为 `253b2213`：UI-010 至 UI-012 已提交，7 个历史 UI 修改文件仍未提交。UI-012 已对包含这些修改的工作区运行完整 UI（41 组，0 失败）和 smoke（21 组，0 失败）；本轮重新核对提交范围，不能把它们当作未知文件直接全量暂存。
- `discovery-baseline.md` 记录了 14 次丢失浏览条件的返回操作。Trellis 父子关系本身不是调度器；本地工作由当前 Codex 会话执行，会话定时续跑提供跨回合恢复。

## Proposed Delivery Stages

### Stage 1: UI stability and delivery

- 收尾现有 UI 修改并完成提交边界审查。
- 从持续 UI 任务中每轮选择一个最高优先级问题，优先处理移动触控目标、导航/字体一致性、遮挡、溢出、焦点和加载状态。
- 对 `/`、`/projects`、`/blog`、`/status`、详情页和 AI Daily 使用桌面、`320/390/430`、三主题、中英文、键盘和 reduced-motion 回归证据。

### Stage 2: Browse and discovery

- 保持现有项目分组，补充可解释的项目查找/筛选体验，不引入未经需求证明的复杂搜索服务。
- 将博客筛选、搜索、分页和可分享状态同步到 URL；返回列表时尽量保留筛选条件、页码和阅读位置。
- 统一空结果、加载、错误和无效详情链接的反馈。

### Stage 3: Content and presentation

- 为重点项目统一“问题、方案、实现、证据、结果、体验入口”的案例结构。
- 校验项目、文章、状态页和助手知识中的名称、状态、链接和公开证据一致性。
- 改善首页首屏项目理解路径和详情页的截图/流程阅读顺序，不改变未经批准的品牌方向或公开事实。

### Stage 4: Language and inclusive interaction

- 评估并修复当前主要只切换导航文案的双语不一致，明确页面正文、筛选、空状态、错误、页脚和辅助标签的语言策略。
- 统一语言/主题偏好持久化、键盘操作、焦点恢复、移动触控目标、弹层和 reduced-motion 行为。

### Stage 5: Public product loops

- 巩固公开助手的冷启动、引用、失败恢复、移动端和隐私边界，并以只读产品证据为准。
- 先完成 AI Daily 单版次“生成、审核、导出、公开 Feed、撤回、回滚证据”闭环，再考虑自动抓取、自动发布或 Cron。
- 任何真实模型调用、生产部署、发布和破坏性数据操作仍由单独人工门禁控制。

### Stage 6: Maintainability and operations

- 补齐必要的 CI、性能预算、链接巡检、SEO、低敏访问分析和回归报告。
- 只引入能回答明确运营问题的观测工具，避免同时接入多套分析或错误追踪服务。

## Requirements

- R1：每个阶段都必须有可独立验收的交付物、文件范围、回滚点和验证命令。
- R2：第一轮审查并交付 Stage 1 已有 UI 成果，完成后重新评估 Stage 2 的列表状态缺陷；实际修改由有完整验收边界的子任务承担。
- R3：普通视觉和交互问题按现有设计令牌、代码约定和浏览器证据直接修复；Stage 2 可在现有路由上实现规范化列表 query 与站内返回。新的品牌方向、公开内容事实、翻译来源、路由/后端数据边界和生产发布仍需单独决策。
- R4：不新增前端框架、后端搜索服务或第三方分析依赖，除非某个阶段的验收明确证明现有实现无法满足目标。
- R5：所有公开内容和助手引用保持可追溯、低敏、证据优先；不伪造项目成果、状态、下载入口或模型能力。
- R6：保留现有 UI 未提交改动、持续 UI 任务、历史任务记录、Logo Lab 资产和旧 worktree；总任务的子任务必须按边界提交。
- R7：Codex 主会话负责实现和最终验证；Trellis 使用 inline 模式，不启动 Claude Code 或其他外部编码流程。
- R8：主任务保存评估依据、当前阶段、唯一活动子任务、验证结果、提交和下一动作。创建下一项之前先恢复未完成子任务，禁止重复建项或并发写同一工作区。
- R9：子任务验收、提交、归档后，必须实际执行 `task.py start` 返回本主任务，更新评估并选择下一项；不能把任务完成通知当成整个循环结束。
- R10：仅当用户停止、授权范围内的候选均完成，或剩余候选全部需要用户决策/外部条件时暂停循环。记录具体原因；不为了维持循环制造无价值工作，也不无限重试相同失败。
- R11：保留“不推送、不部署、不签名、不调用真实生产模型、不公开内容、不修改 public/status/blog-semi-synthetic.json”的既有边界。仅自动化本地开发续跑，不启用业务 Feed/Cron。
- R12：先手动执行完整一轮验证协议，再通过 Codex 原生会话 heartbeat 设置每 15 分钟续跑。正在执行的回合内连续推进，不等待定时器；电脑/应用运行条件或服务失败不属于 Trellis 能保证的连续性。

## Acceptance Criteria

- [x] 用户确认网站完善的首要成功标准为项目理解与内容发现。
- [x] PRD 完成收敛，复杂路线补充 `design.md` 与 `implement.md`；Stage 1-6 均有独立验收边界，实际子任务在进入对应阶段前创建。
- [x] Stage 1 的 UI 交付范围、证据矩阵、提交边界和回滚点明确记录。
- [x] Stage 2 的项目/博客发现体验定义了 URL、返回位置、空/错/加载状态契约。
- [x] Stage 3-6 各有明确进入条件，不把未批准的生产发布或自动化当作默认下一步。
- [ ] 后续实现通过相关 lint、build、UI、内容、SEO、链接和数据安全检查，并保留低敏验证记录。
- [x] 主任务循环协议、状态和首轮项目评估已落档，已完成首次子任务并通过当前会话指针返回主任务。
- [ ] 至少一个实际子任务完成验收和本地交付，随后返回主任务评估并执行下一项。
- [x] 同会话续跑已创建并核对：标识 `automation`，每 15 分钟，ACTIVE，目标为当前会话；未来定时触发尚未观察，不计为已验证。

## Out Of Scope

- 本任务不默认新增登录、会员、支付、社区、CRM、商业线索系统或全站视觉重做。
- 不卸载机器级 Claude CLI，不修改其他项目，不删除历史 worktree，不直接执行生产破坏性操作。
- 整个默认循环均不运行真实生产模型任务、发布公开内容或修改 `public/status/blog-semi-synthetic.json`。
