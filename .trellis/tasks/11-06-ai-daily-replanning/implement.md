## 4. 有意义的验证

新增检查聚焦行为，而非重复实现：

| 场景 | 必须证明 |
| --- | --- |
| 同日两期、UTC/上海跨日、延迟和手动补跑 | 期次稳定、拒绝歧义、早报不被覆盖 |
| 同期重试、分支冲突、只上传部分文件 | 幂等、原子、最新指针不倒退 |
| 全部/部分源失败、空输入、未评分、enrichment failure/partial | 不发布不完整期刊，不把 filtered 摘要当成功 |
| 无 key、超输入预算、取消/超时、限流 | 及时停止，无自动跨渠道或整期无限重跑 |
| 上游 404/超时、损坏/超大 JSON、错误哈希 | 拒绝污染缓存，保留已有内容或真实错误状态 |
| 恶意 Markdown/HTML/URL、details/目录与原文链接 | 安全渲染且阅读功能仍可用 |
| 首期 gate 关闭/开启 | 未验收样稿不进入公开分支；启用后合格期刊自动更新 |

离线阶段按变更范围运行：

```powershell
npm.cmd run lint
npm.cmd run build
npm.cmd run blog:check
npm.cmd run ai-daily:public-payload-check
npm.cmd run ai-daily:public-feed-check
npm.cmd run docs:deployment-check
npm.cmd run docs:manual-gates-check
```

旧 payload/feed 检查用于保留旧契约的回归，并需为新期刊新增对应合同用例，不能仅跑旧检查就宣称新链路通过。Functions 的类型/运行验证按实施时规范执行；原生 helper 的操作签名/配置检查在其独立环境执行。无代码变更的本次规划不跑上述应用测试。

UI 在本地预览验证桌面、320/390/430 宽度、三主题与两种界面语言，检查键盘、目录定位、链接和长文可读性。只有按批准范围发生的真实任务才能证明运行与内容验收，fixture 不能替代。
